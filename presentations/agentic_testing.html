A pattern for tuning interactive simulations

Agentic Testing
of Interactive Simulations

How we put an LLM in charge of the outer loop of haptic force-feedback tuning — and let an optimizer, a metric suite, and an agent-native CLI do the heavy lifting underneath.

Case study · cloth-contact haptics on a surgical-training simulator  ·  Pattern · generic to any interactive sim with tunable parameters

The setup, in plain terms

"Interactive simulation" = a loop with a human in it

A physical stylus your hand holds. A simulated cloth inside the computer. When you push the stylus into the virtual cloth, the device pushes back against your hand — in real time, 1000 updates per second.

The whole value of the simulator depends on the feel of that push-back. Get it wrong and the stylus vibrates in your hand, or feels mushy, or fights you. Get it right and the virtual cloth feels like cloth.

Why tuning this isn't a unit test

Not pass/fail

Outputs are scalars with trade-offs. "Less oscillation" usually costs "slower response." There's no green check; there's a Pareto curve.

Subjective

The thing being optimised is ultimately "how it feels to a hand." You can't write an assert for that — you write proxy metrics and trust them.

Combinatorial

Multiple algorithms × 7 numeric knobs each × multiple scenarios. A human can maybe try 100 configs per day. That's nothing.

Architecture

Three layers, each best at one thing

Stop asking one system to do everything. Split how do we score a run from which knob do we turn from which idea do we try next. Wire the right tool into each layer.

1 · Metrics

Score a run, deterministically

Plain functions that turn a recorded trace into numbers. Did the output buzz with high-frequency noise it shouldn't have? How fast did it respond when the input changed? How smooth was the motion?

Think: a benchmark suite. Latency, tail latency, error rate — but for behaviour quality, not raw perf.

2 · Optimizer

Sweep knobs, find the sweet spot

6–8 numeric parameters with no known-good values. Lowering one metric usually raises another, so there's no single "best" — only a Pareto front of trade-offs. Optuna (NSGA-II) runs ~100 trials/minute against a fast virtual model.

Think: multi-objective hyperparameter search. The "loss" is a vector of competing goals.

3 · Agent (LLM)

Read the Pareto, pick what's next

LLMs can't beat an optimizer at numeric wiggling. They can reason about structure: "oscillation's solved but response is slow — try a different filter architecture." Reads JSON, proposes the next variant, launches another study.

Think: a senior engineer triaging CI output. Doesn't fix every lint — decides which refactor earns a full run.

The contract between layers is a JSON dict. Metrics produce it, optimizer treats it as an objective vector, agent reads it as context. Each layer is replaceable without touching the others — swap Optuna for CMA-ES, swap Claude for GPT-5, add a new metric as new failure modes appear.

The interface

newton-cli: making the machine agent-legible

An agent asked to run a physics scene used to have to emit ~40 lines of Python — imports, Warp types, ModelBuilder calls, a step loop, a solver. One mistake and the whole thing falls over. newton-cli replaces that with two shell calls driven by a JSON recipe.

Why agents love it

  • JSON keys, not code. Agent produces numbers and strings — no risk of wrong imports, wrong types, missing function calls. Agents are good at keys. They're bad at 40-line scripts.
  • Constrained surface. No arbitrary os.remove(). Safety is a side-effect of the CLI being the only entry point.
  • Deterministic exit codes. 0 ok · 2 user err · 3 runtime · 4 missing dep. Agent branches on integers, not on stack-trace substrings.
  • Recipe IS the model. No opaque binary dumps — the JSON is re-executable, diffable, git-friendly. Version-control your scenes like you version-control code.
  • Stateless calls. Files in, files out. No hidden in-process state between invocations.
  • Examples-as-spec. The CLI grew bottom-up from Newton's own examples/. 58 / 65 covered.

What the agent actually emits

// cloth_patch.json
{
  "schema": "newton-cli/recipe/v1",
  "ops": [
    {"op": "add_ground_plane"},
    {"op": "add_cloth_grid",
     "args": {
       "pos":   [-0.5, 2.0, -0.5],
       "dim_x": 10, "dim_y": 10,
       "mass":  0.1,
       "add_springs": true
     }},
    {"op": "set_builder_array",
     "args": {"name": "particle_mass",
              "index": 0, "value": 0.0}}
  ]
}
newton-cli model build --recipe cloth_patch.json \
  --out model.json --json
newton-cli sim run --model model.json \
  --solver SolverXPBD --num-frames 200 \
  --substeps 10 --out state.npz --json
We applied the same contract to our haptic research bench: list-algorithms · run · study · compare. All JSON-in / JSON-out. An LLM drives the whole tuning loop — read the Pareto, pick a structural variant, launch the next study — without ever writing Python.

Case study

Cloth-contact haptic tuning — 60 seconds of compute

We recorded a 2.1 s trace of a real stylus poking into a simulated cloth patch (120 Hz, 257 frames). We asked Optuna to tune 7 parameters of a "virtual coupling" algorithm against a synthetic device model. 100 trials · NSGA-II · one minute wall-clock. It returned a 29-member Pareto front. This is the best pick vs the starting baseline:

What it measures (in plain terms) Technical metric Baseline Tuned Better by
Buzzing in the hand (worst harmonic) oscillation_peak 0.0108 0.00039 27×
Buzzing overall (noise energy) oscillation_rms 0.00481 0.00029 17×
Motion smoothness jerk_rms 132.6 9.64 14×
How fast contact "pops" to full strength rise time (ms) 500 16.7 30×
Phantom force when nothing is touching free_space_force 0.00483 0.0007 7×
Energy the loop "invents" (stability risk) |energy_injection| 0.879 0.005 176×

Strict Pareto Every metric improved simultaneously. No trade-off.

Agent-level insight. The dominant lever turned out to be slew_rate_limit — a rate-of-change cap on the output force. Optuna pushed it to 59× the default. That one hyperparameter had been dominating closed-loop behaviour and masking every algorithmic difference we'd ever compared. A human tuning by hand would almost certainly miss it.

Closing the loop

Offline → virtual → real device

A three-stage funnel. Each stage is slower and more realistic than the last; each stage eliminates most candidates so only the best reach the next.

Stage 1 · Offline

Numeric sweep

Algorithm + synthetic device model + recorded contact trace. Pure numpy. Runs at roughly 1000× real-time. This is what Optuna hammers.

Role: eliminate 95% of candidates cheaply.

Stage 2 · Virtual sim

Full physics, virtual device

Top-N Optuna candidates run through the real simulation pipeline (Newton + Warp) with a virtual device model. Confirms the shortlist holds up under real physics.

Role: catch modelling artefacts before real hardware.

Stage 3 · Real device

Hardware in the loop

The physical stylus is driven to follow the exact recorded trajectory while the tuned algorithm dispatches forces. Same trace, same run, every time. Deterministic A/B on real hardware — without a human.

Role: final validation on the device that will ship.

Making the real-device stage safe

  • Hard force cap well below the device's peak torque.
  • Ramp-in from current pose — no sudden jumps on startup.
  • Tracking-error abort with configurable action: zero / hold / continue.
  • Contact force suppressed during ramp-in so phantom sim-reactions don't fight the position loop.
  • Dry-run scans the trace's kinematics before anything touches hardware.

Next horizons

  • Live-tweak. MCP server exposes the running sim to an agent; parameters adjust mid-session with a human on the stylus.
  • Auto-generated algorithms. Agent composes new compute_force() variants from a library of primitives (passivity controllers, Kalman predictors, wave variables).
  • Cross-asset transfer. Do cloth-tuned presets hold up on liver, on gallbladder, on fat? If not — overnight per-asset mini-studies.
Takeaway. Structured I/O + deterministic replay + a clean agent / optimizer / metric split turns an interactive simulation's qualitative tuning problem into overnight CI. The newton-cli pattern — JSON in, JSON out, integer exit codes, stateless calls — is the contract that makes it work. The technique isn't specific to haptics; it's what you reach for any time "quality" means a vector of trade-offs instead of a pass/fail.
